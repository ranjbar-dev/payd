# payd — full repository review, 2026-08-10

Reviewer: staff-level Go engineer, adversarial pass over the whole tree.
Method: package/dependency map → request path → money path (deposit detection →
confirmation → credit → withdrawal → settlement), then targeted reads of every
file that mutates state, touches keys, or accepts untrusted input. Specs in
`docs/specs/` and `AGENTS.md` read first and used as the oracle.

Tooling actually run, real output:

```
$ go build ./...          # clean, no output
$ go vet ./...            # clean, no output
$ go test ./...           # Go test: 191 passed in 19 packages
$ gofmt -l .
internal\api\api_test.go
internal\api\withdrawals.go
```

Coverage: complete for security, the money path, architecture, and the
performance claims below. Not covered: `internal/api/api_test.go` and the other
test files were read only where they bore on a finding; the `hd-wallet`,
`memguard`, and `modernc.org/sqlite` dependencies were not audited internally;
no dynamic/fuzz testing was performed.

---

## 1. Executive summary

The engineering is genuinely good. Money is `big.Int`/`big.Rat` decimal strings
end to end with no float anywhere, every fund-moving broadcast sits behind a
durable single-attempt marker, SQL is parameterised throughout, and the
requirement-ID comments make the code auditable against its own spec. The
crash-safety design in `internal/withdraw` is better than most production
payment code I have read.

Fix first, in order:

1. **Rotate and untrack `payd.nile.yaml`.** It is committed and pushed to
   `origin/main` with a *working* API key in a comment (verified against its own
   Argon2id hash) and the live TOTP secret — the withdrawal second factor.
2. **The confirmation promotion window is bounded by block retention.** A
   ~2.5-minute confirm-worker outage strands payments in `seen` permanently:
   orders never confirm, balances never become spendable.
3. **Argon2id (64 MiB, ~50 ms measured) runs before rate limiting on every
   unauthenticated request.** Twenty concurrent sockets is ~1.3 GB of RSS.

Would I let this hold real money today? No — not until (1) and (2) are closed.
After those two, yes, behind TLS on a loopback bind, with (3) and the response
buffering in `normalizeErrors` fixed in the same week.

**C1. A working API key and the withdrawal TOTP secret are committed and pushed**

`payd.nile.yaml:17`, `payd.nile.yaml:104`, `payd.nile.yaml:107`

`.gitignore` correctly excludes `seed.age`, `*.db`, `*.exe` and

`auth.api_keys[].key_hash` with the plaintext key written next to it in a

recomputed `argon2id(m=65536,t=3,p=2)` over
`45k653AmthF070ei0qzifoGXIPfjyqNXpeXG-UNtAb0` with the committed salt and it
reproduces the committed hash exactly. `totp_secret` is the *only* second factor
protecting `POST /withdrawals` and `POST /withdrawals/{id}/resolve`.

Failure scenario: anyone who can read the repository (or any clone, fork, CI
cache, or GitHub search index) sends `X-API-Key: 45k653Am…` plus
`X-TOTP: $(paydev totp W4GJIBZ5VLM7HAUQPYNVSPHXLRZENCDT)` to a reachable payd
and has authenticated withdrawal capability. This instance names Nile endpoints,
so the funds at risk here are testnet — but the credential pattern is what ships
to mainnet, and `docs/specs/04-configuration.md:14` shows `listen: "0.0.0.0:8080"`.

Fix, smallest that works:

```bash
git rm --cached payd.nile.yaml
printf 'payd.*.yaml\n!payd.example.yaml\n' >> .gitignore
```

Then rotate all three secrets (`paydev apikey`, `paydev totp-secret`, new
TronGrid key) and purge the blobs from history (`git filter-repo` or a fresh
squash) since the old commits stay fetchable. Never write a plaintext key beside
its hash — the hash exists precisely so the plaintext does not have to live
anywhere. Confidence: **CONFIRMED** (hash recomputed and matched).

### HIGH

---

**H1. Payments fall out of the confirmation window forever if the confirm worker stalls for ~2.5 minutes**

`internal/store/confirm.go:135`, `internal/store/follower.go:261`

`promotablePayments` anchors a recursive CTE at `blocks WHERE height =
lastHeight` and inner-joins `payments` to it. `CommitBlock` deletes
`blocks WHERE height < block.Height - reorgDepth` on every ingest. So a payment
is promotable only while its block row still exists *and* is at least
`confirmations_required` behind the tip: `block_height ∈ [lastHeight-64,
lastHeight-19]` with the shipped config. At TRON's 3 s block time that is 46
heights ≈ **138 seconds**. `Confirm.Run` ticks every 20 s
(`internal/confirm/worker.go:51`); six consecutive failures — one solidity-node
outage — and the block row is gone. No other code path ever writes
`payments.status = 'confirmed'` (verified: the only `UPDATE payments SET`
statements are `confirm.go:64`, `confirm.go:76`, `follower.go:414` and
`orders.go:540`, and none of them re-promote a stale `seen` row).

Failure scenario: customer pays order X at height H. The solidity endpoint 502s
for three minutes. Cursor advances past H+64, the block row is trimmed. Payment
X stays `seen` forever → `recalculateBalance` keeps it in `pending_raw`, never
`confirmed_raw` → order stays `paid`, never `confirmed`, so `order.confirmed`
IPN never fires and the merchant never ships → and the received funds are
permanently unwithdrawable, because `CreateWithdrawal`
(`internal/store/withdrawals.go:168`) and `ClaimWithdrawal` (`:313`) both spend
only `confirmed_raw`. Silent: `/readyz` goes green again the moment solidity
recovers.

Fix: stop deriving ancestry from the trimmed `blocks` table for old payments.
The cheapest correct change is to keep the CTE for the recent window and add a
fallback for payments below the retained floor, where solidified height is
already proof of irreversibility:

```sql
-- in promotablePayments, replace the plain JOIN with:
FROM payments p LEFT JOIN canonical b ON b.height = p.block_height
WHERE (p.status='seen' OR (p.status='unattributed' AND p.confirmed_at IS NULL))
  AND p.block_height <= ?                                   -- solidified
  AND (b.block_id = p.block_id                              -- in retained window: ancestry proven
       OR p.block_height < (SELECT MIN(height) FROM blocks)) -- below floor: solidity is the proof
  AND ? - p.block_height >= ?
  AND (? IS NULL OR p.block_height < ?)
```

Add a regression test that advances the cursor 100 blocks with the confirm
worker paused, then runs one tick and asserts the payment promotes. Confidence:
**CONFIRMED**.

**H2. Argon2id runs before rate limiting on unauthenticated requests**

`internal/api/server.go:92`, `internal/api/middleware.go:43`

The chain is `root.Handle("/", server.authenticate(server.rateLimit(mux)))` —
`authenticate` is *outside* `rateLimit`. For every request that fails auth,
`authenticate` runs `argon2.IDKey` once per configured key at
`m=65536,t=3,p=2`, then returns 401 without ever reaching the limiter. And the
limiter keys on `state.keyName`, which is empty for unauthenticated callers
anyway, so it could not throttle them even if it ran first. I measured
**50.3 ms and 64 MiB per hash** on this machine.

Failure scenario: `for i in $(seq 1 40); do curl -H 'X-API-Key: x'
http://payd:8080/api/v1/stats & done` in a loop. Go's `http.Server` imposes no
concurrency cap, so 40 in-flight requests allocate ~2.6 GB and saturate every
core. The process OOMs or the follower's SQLite writes starve. One key in the
config; multiply by N keys. The comment at `server.go:87` justifies the public
routes with "`server.listen` defaults to 127.0.0.1", but
`docs/specs/04-configuration.md:14` documents `0.0.0.0:8080`.

Fix: swap the wrapping so the limiter sees unauthenticated traffic, and give it
a fallback identity:

```go
root.Handle("/", server.rateLimit(server.authenticate(mux)))
// in rateLimit:
identity := state.keyName
if identity == "" {
    identity, _, _ = strings.Cut(r.RemoteAddr, ":") // pre-auth bucket
}
```

Cap the pre-auth bucket low (10/min) and evict `s.rates` entries older than a
minute so the map cannot grow with attacker-chosen IPs. Confidence:
**CONFIRMED** (cost measured, not estimated).

**H3. Every response is fully buffered in memory, so the CSV exports are not streamed**

`internal/api/middleware.go:92`, `internal/api/middleware.go:107`, `internal/api/export.go:45`

`normalizeErrors` wraps the entire mux in a `bufferedResponse` whose `Write`
appends to a `bytes.Buffer`, and only flushes after the inner handler returns.
`exportOrdersCSV` and `exportWithdrawalsCSV` were written as streaming handlers
(`StreamOrders` with a visitor, `csv.Writer` over `w`) — the middleware silently
defeats that. `exportLimit` allows up to 100 000 rows, and the orders CSV
includes the caller-controlled `metadata` column, which `decodeJSON` caps at
1 MiB per order.

Failure scenario: an `orders:read` key issues
`GET /api/v1/export/orders.csv?limit=100000`. The whole CSV materialises in RAM
before a byte reaches the socket. With realistic 2 KB metadata that is ~200 MB
per request; the withdrawals bucket allows 10/min and the default bucket 100/min,
so a handful of concurrent exports exhausts memory. Even benign use gives the
operator a multi-second stall with no progressive output.

Fix: only buffer what you need to rewrite, which is a status line and an empty
body. Make `bufferedResponse` pass through once the handler has committed to a
2xx:

```go
func (w *bufferedResponse) Write(b []byte) (int, error) {
    if w.status < 400 {                 // nothing left to normalise
        if !w.wroteHeader {
            copyHeader(w.real.Header(), w.header)
            w.real.WriteHeader(w.status)
            w.wroteHeader = true
        }
        return w.real.Write(b)
    }
    return w.body.Write(b)
}
```

Cheaper alternative if you want zero middleware surgery: exempt the two
`/api/v1/export/` paths from `normalizeErrors` — they already set their own
`Content-Type`. Confidence: **CONFIRMED**.

**H4. No TLS, and the documented bind is `0.0.0.0`**

`cmd/payd/main.go:205`, `docs/specs/04-configuration.md:14`

`httpServer.ListenAndServe()` — plain HTTP, no `ListenAndServeTLS`, no
certificate config field, and no mention of TLS, a reverse proxy, nginx or caddy
anywhere in `QUICKSTART.md` or `docs/specs/17-operations.md` (grepped). The API
key and the TOTP code travel as request headers.

Failure scenario: an operator follows `docs/specs/04-configuration.md`, binds
`0.0.0.0:8080`, and calls the withdrawal endpoint from a laptop. Anyone on the
path sees `X-API-Key` and `X-TOTP` in cleartext. The TOTP code is single-use and
90-seconds-valid, but that is a comfortable window for an active attacker who
already has the key — and the key alone grants every read scope plus
`orders:write`.

Fix: this is a docs + deployment change, not a code change — do not add TLS
termination to the process. Change the spec example to `127.0.0.1:8080`,
document the reverse proxy as mandatory in `17-operations.md`, and make
`Validate()` refuse a non-loopback `server.listen` unless an explicit
`server.trusted_proxy: true` is set. Confidence: **CONFIRMED**.

**M1. `/metrics` is unauthenticated and exposes business volume and treasury state**

`internal/api/server.go:89`, `internal/ops/ops.go:80`

`publicRoutes` bypasses `authenticate` entirely, and the comment justifying it

`payd_balance_drift_addresses`, `payd_energy_provider_balance_trx`, and IPN

Failure scenario: with the documented `0.0.0.0` bind, a competitor scrapes
`/metrics` every 30 s and reconstructs daily payment volume, treasury size, and
whether an operator intervention is currently pending — the last being a useful
signal for timing anything else.

Fix: leave `/healthz` and `/readyz` public (probes need them); move `/metrics`,
`/openapi.yaml` and `/docs` behind `authenticate`, or gate `/metrics` on a
separate `server.metrics_listen` bound to loopback. Confidence: **CONFIRMED**.

**M2. `GET /api/v1/withdrawals` accepts a cursor, ignores it, and returns no `next_cursor`**

`internal/api/withdrawals.go:116`, `internal/api/withdrawals.go:130`

`limit, _, err := pagination(r, false)` discards the parsed cursor, and the
response body is `{"items": …}` with no `next_cursor`. Every other list endpoint
in the API returns a cursor and honours it. `store.ListWithdrawals` has no
`After` parameter at all.

Failure scenario: a reconciliation script pages through withdrawals the way it
pages through orders. It gets page 1, finds no `next_cursor`, and concludes it
has seen everything — silently missing every withdrawal beyond the 200-row cap.
Books balance against a truncated set.

Fix: add `After string` to the `ListWithdrawals` signature, mirror
`ListOrders`'s `AND w.id < ?` keyset (the ordering is `created_at DESC, id
DESC`, so the predicate is `<`, not `>`), and emit `next_cursor` like
`listOrders` does. Confidence: **CONFIRMED**.

**M3. CSV formula injection in the orders export**

`internal/api/export.go:50`

`order.Metadata` and `external_ref` are written to the CSV verbatim. Both are
attacker-controlled: `external_ref` is a free string on `POST /orders`, and
`metadata` is any JSON object.

Failure scenario: a merchant integration (or anyone with `orders:write`) creates
an order with `"external_ref": "=cmd|'/c calc'!A1"`. An operator opens
`orders.csv` in Excel and the cell is evaluated as a DDE formula. Same for a
metadata value.

Fix: prefix a single quote when a field starts with a formula lead-in, in the
one place both exports funnel through:

```go
func csvSafe(v string) string {
    if v != "" && strings.ContainsRune("=+-@\t\r", rune(v[0])) {
        return "'" + v
    }
    return v
}
```

Confidence: **CONFIRMED**.

**M4. `/docs` loads Swagger UI from a CDN and tells it to persist the API key**

`internal/api/docs.go:18`, `internal/api/docs.go:22`, `internal/api/docs.go:23`

The embedded HTML pulls CSS and JS from `cdn.jsdelivr.net` with no SRI hash and
no pinned version (`swagger-ui-dist@5` floats), on an unauthenticated route, and
passes `persistAuthorization: true` — which makes Swagger UI store whatever the
operator typed into its Authorize box in `localStorage` on payd's own origin.

Failure scenario: jsdelivr serves a tampered `swagger-ui-bundle.js` (supply-chain
compromise, or a floating `@5` that ships a bad release). The script runs on
payd's origin and reads the operator's live API key straight out of
`localStorage`, then POSTs it out. No payd bug required.

Fix: `go:embed` the two Swagger UI assets next to `openapi.yaml` and serve them
from payd, or drop `/docs` entirely and let operators point their own Swagger at
`/openapi.yaml`. At minimum, pin an exact version and add an `integrity`
attribute, and set `persistAuthorization:false`. Confidence: **CONFIRMED**.

**M5. One malformed Transfer log from a configured token stalls chain ingest indefinitely**

`internal/decode/decode.go:310`, `internal/follower/follower.go:196`

`credit` returns a hard error when a log from an allowlisted contract carries
the `Transfer` topic0 with fewer than three topics. That error propagates
through `Prepare` → `commit` → `Tick`, which returns before advancing the
cursor. The next tick re-fetches the same block and fails identically. The
`halted` flag is never set, so `/readyz` reports `chain_lag` only after 20
blocks — about a minute later.

Failure scenario: an operator adds a TRC-20 token that emits `Transfer` with
non-indexed `from`/`to` (legal ERC-20/TRC-20 — indexing is a convention, not a
requirement). The first such transfer anywhere in a block permanently wedges the
follower at that height. Deposits stop being detected chain-wide, not just for
that token.

Fix: a log shape you cannot decode is not an ingest error, it is a log you skip.

```go
if len(log.Topics) < 3 {
    continue // non-indexed Transfer: nothing attributable here
}
```

Note the same reasoning applies to every `return nil, fmt.Errorf(...)` inside
`screen`/`credit` that is driven by chain data rather than by a payd invariant.
Confidence: **CONFIRMED** for the topics case; the surrounding address/amount
errors are unreachable today because TronGrid emits well-formed hex.

**M6. `recalculateBalance` full-scans `payments` on every payment write**

`internal/store/follower.go:459`, `internal/store/migrations/001_initial.sql`

The predicate is `address_id=? OR (direction='out' AND to_address=(SELECT
address FROM addresses WHERE id=?))`. `payments.to_address` has no index, and
the `OR` blocks `idx_payments_addr_asset`, so SQLite scans the whole table. This
runs once per payment in `UpsertPayment`, again for the owned-recipient branch,
and once per affected balance in `ApplySolidifiedHeight` and `RewindChain`.

Failure scenario: at 500 000 payment rows (a year of moderate traffic on a
500-address pool), a block containing 10 payments costs ~20 full scans inside
the single write transaction, on the *single* SQLite writer connection. Block
ingest falls behind the 3 s poll, `chain_lag` fires, and the confirm worker —
see H1 — is now competing for the same connection.

Fix: `CREATE INDEX idx_payments_to_address ON payments(to_address, asset) WHERE
direction='out';` and split the OR into a `UNION ALL` of two indexed queries so
the planner can use both. Confidence: **CONFIRMED** (query shape read against
the schema; not benchmarked at scale — the row count above is the threshold I
would expect it to bite, not a measurement).

**M7. `GET /api/v1/wallets` issues a price and chain-parameter query per wallet per asset**

`internal/api/wallets.go:179`, `internal/api/wallets.go:190`

`writeWalletPage` loads *all* addresses, paginates in Go, then calls
`walletJSON` per item. `walletJSON` calls `price.Current` (one
`SELECT … FROM prices`) for every balance and `LoadChainParameters` once per
wallet.

Failure scenario: `?limit=200` against a 500-address pool with 4 configured
assets is 200 × (4 + 1) = 1 000 round trips on the single-writer connection,
plus the initial unbounded `walletAddresses` join. At the default 100 req/min
rate limit an authenticated key can hold that connection continuously and starve
block ingest.

Fix: hoist both out of the loop — snapshot `s.store.Prices(ctx)` and
`LoadChainParameters(ctx)` once in `writeWalletPage` and pass them down. Push
`LIMIT`/keyset into `WalletAddresses` while you are there. Confidence:
**CONFIRMED**.

**M8. `OrderPayments` and `AddressPayments` have no `LIMIT`**

`internal/store/api.go:125`, `internal/store/api.go:130`

Both call `listPayments(..., 0, 0)`, and `listPayments` only appends `LIMIT`

**M9. Fund-adjacent operator actions have no second factor**

`internal/api/routes.go:30`, `internal/api/routes.go:31`, `internal/store/wallet.go:256`

`POST /wallets/{address}/delegate` broadcasts a real on-chain Stake 2.0
delegation from the resource wallet (`withdraw.DelegateResources` →
`startDelegation` → `broadcastResourceGrant`) behind `resources:write` alone.
`POST /wallets/{address}/clear-drift` clears `drift_detected` behind
`wallets:write` alone — and `drift_detected` is the flag that
`CreateWithdrawal:163` and `ClaimWithdrawal:288` use to *refuse* spending from
an address whose ledger and chain balances disagree.

Failure scenario: a leaked `wallets:write` key clears drift on an address where
reconciliation found the chain balance short. The next withdrawal from that
address is no longer blocked, and payd signs a transfer for an amount the chain
cannot cover — burning energy and bandwidth on a guaranteed
`CONTRACT_VALIDATE_ERROR`, or worse, succeeding against a balance the ledger has
already double-counted elsewhere. `clear-drift` also never re-reads the chain
before clearing.

Fix: require `X-TOTP` on both, exactly as `resolveWithdrawal` does
(`withdrawals.go:161`). For `clear-drift`, additionally require the caller to
echo the current `chain_raw` value they are accepting, so clearing is an
acknowledgement of a specific number rather than a blanket reset.

```go
if err := s.ValidateTOTP(r.Context(), r.Header.Get("X-TOTP"), time.Now()); err != nil {
    writeError(w, http.StatusUnauthorized, "invalid_totp", "TOTP is invalid or already used", nil)
    return
}
```

Confidence: **CONFIRMED**.

**M10. Energy-provider HTTP calls ignore context; shutdown and request cancellation cannot reach them**

`internal/energy/provider.go:168`

`tronZap.post` uses `http.NewRequest`, not `http.NewRequestWithContext`, and the
`Provider` interface (`provider.go:21`) takes no `context.Context` at all. Every
caller in `internal/withdraw` has a context and cannot pass it.

Failure scenario: `estimateWithdrawal` (`withdrawals.go:206`) calls
`EstimateResources` → `provider.Quote` on the request goroutine. A client
disconnects; the goroutine stays blocked for the full `energy.timeout` (15 s
configured). Same at shutdown: `workers.Wait()` in `main.go:216` blocks behind
an in-flight provider call the 10 s shutdown budget cannot cancel.

Fix: add `ctx context.Context` as the first parameter of all four `Provider`
methods and thread it into `http.NewRequestWithContext`. Mechanical, ~20 lines,
and it is the only remaining place in the codebase where an outbound call is not
context-bound.

**M11. `validateBurnCeiling` hardcodes 131 000 energy instead of `resources.min_energy`**

`internal/chain/params.go:138`

`requiredSun := energy.BurnCostSun(131000, energyFee)` — the literal matches the
shipped `resources.min_energy`, but the readiness check is supposed to answer
"can `max_burn_trx` still fund a worst-case transfer", and that worst case is
whatever `min_energy` is configured to be. `sourceEnergy` (`engine.go:617`) and
`EstimateResources` (`engine.go:160`) both use the configured value.

Failure scenario: operator raises `resources.min_energy` to 200 000 for a
heavier contract but leaves `max_burn_trx: "60"`. `ENR-017` computes against
131 000, finds the ceiling adequate, and `/readyz` stays green — while every
TRC-20 withdrawal that needs a burn fails with `energy_burn_limit` and lands in
`needs_operator`. The one signal designed to catch this is looking at the wrong
number.

Fix: plumb `cfg.Resources.MinEnergy` into `ParameterWorker` alongside
`maxBurnTRX` (it already has an `UpdateMaxBurnTRX` reload path to extend) and
use it. Confidence: **CONFIRMED**.

**M12. One synchronous SQLite write per TronGrid RPC, taken under the counter mutex**

`internal/chain/client.go:345`, `internal/store/operations.go:19`

`sendOnce` calls `counter.increment` before every HTTP request, which holds
`dailyCounter.mu` across an `INSERT … ON CONFLICT … RETURNING` on the shared
single-connection `normal` handle. So every chain read serialises behind the
same writer that block ingest, confirmation, and the API use — and a write
failure aborts the RPC entirely (`return Response{}, fmt.Errorf("record
TronGrid request: %w", err)`).

Failure scenario: block ingest opens a long write transaction (see M6 at high
row counts). Concurrent RPCs from the follower's receipt fetch, the resource
monitor's two tiers, and the withdrawal engine all block on `busy_timeout(5000)`,
then fail. Chain reads stop because a *metrics counter* could not be written.

Fix: keep the counter in memory and flush it on a timer. The RL-006 seven-day
trend needs durability across restarts, not per-request durability:

```go
// increment: bump c.count in memory only.
// separate goroutine, every 10s: UPSERT the current day's total.
```

Confidence: **CONFIRMED** for the coupling; the contention threshold is the same
scale as M6 and was not measured.

### LOW

**L1. A valid TOTP code is consumed before the withdrawal can be rejected**
`internal/api/withdrawals.go:72`. `ValidateTOTP` inserts into `used_totp` before
`CreateWithdrawal` runs, so a rejection for `daily_limit_exceeded` or
`insufficient_confirmed_balance` burns the code and the operator waits up to 30 s
for the next one. Moving TOTP consumption after the store call would break the
WDR-001a ordering the spec calls for, so the smallest honest fix is to say so in
the 409 body (`"details": {"totp_consumed": true}`). Arguably accepted risk.
**CONFIRMED**.

**L2. `classifyBroadcast`'s final `if/else` returns the same value on both arms**
`internal/withdraw/engine.go:1291`. Dead branch — `if sendErr != nil || …
{ return "ambiguous", code }` followed by `return "ambiguous", code`. Collapse to
one return. The behaviour is correct (ambiguity is the safe default), the code
just reads as if it discriminates when it does not. **CONFIRMED**.

**L3. `RecordWithdrawalLookup` concatenates a SQL fragment**
`internal/store/withdrawals.go:514`. `status := "status"` / `"'broadcast'"` then
`"UPDATE withdrawals SET status=" + status`. Not injectable — both values are
literals — but it is the one place in `internal/store` where a query is built by
concatenation rather than parameters, and it will read as a finding to the next
auditor. Rewrite as `SET status = CASE WHEN ? THEN 'broadcast' ELSE status END`
with `found` bound. **CONFIRMED**.

**L4. `internal/seed/seed.key` is mode 0644** — the 32-byte deployment key that
decrypts `seed.age`. Irrelevant on this Windows box and it is build-time-only,
but on the Linux build host it is world-readable. `chmod 600`. The residual risk
of the embedded key itself is explicitly documented and accepted in
`docs/specs/14-key-management.md`, so it is not a finding.

**L5. `audit_log` and `payments` have no retention policy**
`internal/store/migrations/001_initial.sql`. `used_totp` is pruned
(`lifecycle/worker.go:82`), nothing else is. Fine for a year; worth a decision

## 3. Architecture assessment

**What the structure makes easy.** The package split matches the worker split,
and `AGENTS.md`'s three structural rules (workers never call each other; all
writes through `internal/store`; no network I/O inside a write transaction) are
actually upheld — I checked every write path and found no violation. The
`Prepare`/`BlockApply` split in the follower is the good idea in this codebase:
it makes "finish all RPC, *then* open the transaction" a type-level property
instead of a convention, and `decode.Prepare` returning a closure that can only
touch `*BlockWrite` is exactly the right shape. `ReadClient`/`BroadcastClient`
splitting the retry loop by *type* — `Send` is not a method on `ReadClient`, so
it cannot reach `do` — makes the no-retry-on-broadcast invariant unbypassable
rather than merely documented. Requirement IDs in comments mean I could check
code against spec in minutes instead of hours.

**What it makes hard.**

*One connection, one lock, everything.* `SetMaxOpenConns(1)` on both handles
turns every SQLite call into a global mutex. That is the correct call for
correctness, but it means every N+1 in the API (M7), every full scan in the
ledger (M6), and every metrics write (M12) is direct contention with block
ingest. There is no read pool. The cheapest structural fix is a third, read-only
handle with `SetMaxOpenConns(N)` — WAL supports concurrent readers — used by
every `List*`/`Get*` path that does not need to see uncommitted writes.

*Block retention doubles as the confirmation ledger.* H1 is not a typo, it is a
coupling: `reorg_depth` controls both how far back a reorg can be repaired and
how long a payment stays eligible for promotion. Those are different questions
with different right answers, and nothing in the code says they are joined.

*`internal/store` is the domain layer by accretion.* 3 600 lines across 14 files,
holding SQL, money arithmetic (`ParseUnits`, `FormatUnits`, `rationalDecimal`),
event payload construction, and business rules (`recalculateOrderWithTransition`
decides order status transitions; `ClaimWithdrawal` decides fund sufficiency).
That is why `internal/api` reaches so deeply into it and why the money rules
have no test that does not need a database. It works, and I would not rewrite it
— but the next thing that hurts will be a rule that lives in SQL and cannot be
unit-tested.

*Config reload has fifteen `UpdateX` calls.* `main.go:236`–`:259` fans one
reload out to fifteen components, several of which take the whole `Config` and
copy the three fields they want. Adding a sixteenth reloadable component means
remembering to add a sixteenth line, and nothing catches a forgotten one.

**Ranked by payoff/effort:**

| # | Change | Effort | Payoff |
|---|---|---|---|
| 1 | Decouple promotion eligibility from block retention (H1) | S | Removes the only silent fund-stranding bug |
| 2 | Add a read-only `*sql.DB` with a real connection pool | S | Removes API-vs-ingest contention wholesale |
| 3 | Swap `authenticate`/`rateLimit`, add pre-auth bucket (H2) | S | Closes trivial remote DoS |
| 4 | Pass through 2xx bodies in `normalizeErrors` (H3) | S | Makes exports actually stream |
| 5 | Add `ctx` to the `energy.Provider` interface (M10) | S | Last uncancellable outbound call |
| 6 | Index `payments.to_address`, split the `OR` (M6) | S | The ledger's only full scan |
| 7 | Replace 15 `UpdateX` calls with one `Reloadable` interface + slice | M | Removes a whole class of reload bug |
| 8 | Lift order-status transition rules out of SQL into a testable Go function | M | Money rules become unit-testable |

**Delete or simplify, not add:**

- `store.FundedTerminalOrders` (`orders.go:455`) — dead, duplicates
  `ListFundedTerminalOrders`.
- One of `decimalRat` / `rationalDecimal`, and one of the two `configuredAsset`
  copies.
- The dead `if/else` in `classifyBroadcast` (`engine.go:1291`).
- `Server.ValidateWithdrawalSource` (`wallets.go:237`) — no caller; the
  withdrawal handler calls `store.BalanceForWithdrawal` directly.
- The `eventConfigs ...EventConfig` variadic-of-one pattern
  (`follower.New`, `lifecycle.New`, `store.ExpireOrders`, `store.RewindChain`).
  Four places take an optional single value as a variadic slice; make it a plain
  parameter, since every call site passes exactly one.

**Test coverage of the money path.** 191 tests pass and the withdrawal state
machine is well covered (`engine_test.go`, 842 lines, including the
`DUP_TRANSACTION_ERROR` regression TST-014 asks for). The gaps that matter:

- **No test that a payment survives a confirm-worker outage.** That is H1, and
  it is untested precisely because the promotion window is invisible from
  outside `promotablePayments`.
- **No test of `recalculateBalance` for the owned-to-owned case.** The
  synthetic-fee row (`ConfirmWithdrawal:665`, `log_index=-1`) and the
  owned-recipient credit (`UpsertPayment:319`) both feed the same balance and
  are only exercised indirectly.
- **No concurrency test on `CreateWithdrawal`/`ClaimWithdrawal`.** The daily-cap
  `payd_decimal_sum_within` guard and the per-address `NOT EXISTS` claim are the
  two conditional writes that stop double-spend, and both are only tested
  serially.
